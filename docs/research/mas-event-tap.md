# Can a sandboxed event-tap keyboard utility pass Mac App Store review?

Research for issue #32 (parent map #31). Researched 2026-11-28.

**Verdict: feasible with caveats.** The two OS facilities Pāli Key needs on macOS (listening to keystrokes and posting synthetic keystrokes) are both compatible with the App Sandbox according to Apple DTS. The real risk is App Review: reviewers have rejected sandboxed apps that post keystrokes under Guideline 2.4.5, and review outcomes are reported as inconsistent. A newly submitted, fully sandboxed text expander (TypeIt4Me 7, 2025) is on the store, so it can pass.

Legend: **Fact** = stated by a primary source (Apple docs, SDK headers, Apple staff on the Developer Forums, App Store listings). **Inference** = our reasoning, not stated by Apple.

## 1. Can a sandboxed app tap and post keyboard events?

### Three different TCC privileges, two of them sandbox-compatible

- **Fact.** There are three separate TCC privileges: `ListenEvent` (system-wide event monitoring, e.g. a CG event tap), `PostEvent` (posting UI events, e.g. `CGEvent.post(tap:)`) and `Accessibility` (accessibility products, e.g. inspecting other apps' UI). In System Settings, `ListenEvent` shows as **Input Monitoring**, while both `PostEvent` and `Accessibility` show as **Accessibility**. Quinn "The Eskimo!" (DTS), Mar 2026: "The APIs gated by the `Accessibility` privileged are not compatible with the App Sandbox ... The APIs gated by the other two privileges _are_ compatible with the App Sandbox." He adds that in his experience the Mac App Store sandbox requirement "isn't an impediment to apps that rely on the `PostEvent` and `ListenEvent` privileges." Source: [forums thread 820594](https://developer.apple.com/forums/thread/820594).
- **Fact.** A listen-only `CGEventTap` uses Input Monitoring, which "is easily available to sandboxed apps, and even apps published on the Mac App Store", with `CGPreflightListenEventAccess` / `CGRequestListenEventAccess` to check and request it. Source: Quinn, [thread 707680](https://developer.apple.com/forums/thread/707680) (2022); repeated in [thread 811443](https://developer.apple.com/forums/thread/811443) (Jan 2026, "macOS 10.15 and later") and [thread 780626](https://developer.apple.com/forums/thread/780626) (Apr 2025, "I regularly test this").
- **Fact.** Posting keyboard events from a sandboxed App Store app: "You can post events using `CGEvent.post(…)`. That uses its own privilege, one that's also compatible with App Sandbox ... While this privilege shows up in the UI as System Settings > Privacy & Security > Accessibility, it doesn't give you complete accessibility access. It's just limited to posting events." Posting triggers the TCC alert automatically, or use `CGPreflightPostEventAccess` / `CGRequestPostEventAccess`. Source: Quinn, [thread 789896](https://developer.apple.com/forums/thread/789896) (Jun and Oct 2025). Same advice for a sandboxed "delete then cmd+V" snippet app in [thread 708652](https://developer.apple.com/forums/thread/708652) (2022): explicit user approval introduced in 10.15 "means that it's now allowed in the App Sandbox."
- **Fact.** The four access functions exist in the SDK since macOS 10.15: `CGPreflightListenEventAccess`, `CGRequestListenEventAccess`, `CGPreflightPostEventAccess`, `CGRequestPostEventAccess` (`CoreGraphics/CGEvent.h`, macOS 27.2 SDK; [Apple docs](https://developer.apple.com/documentation/coregraphics/cgrequestposteventaccess())).
- **Fact.** `NSEvent.addGlobalMonitorForEvents` needs the full Accessibility privilege, not Input Monitoring, so it is the wrong API for a sandboxed app ([thread 707680](https://developer.apple.com/forums/thread/707680), [thread 820594](https://developer.apple.com/forums/thread/820594) footnote).
- **Fact.** `CGEventKeyboardSetUnicodeString` (`keyboardSetUnicodeString`) overrides the string of a keyboard event, but "application frameworks may ignore the Unicode string in a keyboard event and do their own translation based on the virtual keycode" ([Apple docs](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring(stringlength:unicodestring:))). Per-app compatibility testing is needed.

### What does not work in the sandbox

- **Fact.** Apple's App Sandbox documentation lists "Use of accessibility APIs in assistive apps" and "Simulating user input in Open and Save dialogs" among activities "forbidden by the operating system when an app runs in a sandbox" ([Protecting user data with App Sandbox](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox#Review-functionality-that-is-incompatible-with-App-Sandbox)).
- **Fact.** `AXUIElementCreateApplication` (reading another app's accessibility tree) is not possible in a sandboxed app (Quinn, [thread 756130](https://developer.apple.com/forums/thread/756130), 2024). So Pāli Key must not read the focused text field through AX; the Input Buffer must be built only from tapped keystrokes, as on Windows.
- **Community report, not Apple.** Event taps targeting a specific pid (`CGEventTapCreateForPid`) reportedly do not work in the sandbox ([thread 750172](https://developer.apple.com/forums/thread/750172)). Use a session-wide tap.

### Active (filtering) tap versus listen-only tap: unresolved

- **Fact.** An active filter tap "may pass an event through unmodified, modify an event, or discard an event"; a passive listener cannot ([CGEventTapOptions](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions)). The SDK header still describes key-event access in pre-TCC terms ("access for assistive devices").
- **Community report, not Apple.** A `defaultTap` (active) triggers the Accessibility prompt, a `listenOnly` tap triggers the Input Monitoring prompt ([thread 122492](https://developer.apple.com/forums/thread/122492), 2021). No Apple statement found on whether an active tap's privilege is `PostEvent` (sandbox-compatible) or full `Accessibility` (not compatible).
- **Inference.** Pāli Key can avoid the question: use a listen-only tap to build the Input Buffer and perform the Replacement purely with posted events (Backspace(s) plus the Pāli character), so it needs only `ListenEvent` + `PostEvent`. Swallowing the triggering key (e.g. the Diacritic Key `f`) needs an active tap; without it the `f` reaches the app and must be erased too (one more Backspace). This must be verified in a sandboxed prototype on a clean VM, as Quinn advises cached TCC state misleads tests ([thread 811443](https://developer.apple.com/forums/thread/811443)).

## 2. Does App Review accept it? Precedents and rejections

- **Fact.** Guideline 2.4.5(i): Mac App Store apps "must be appropriately sandboxed" ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/)). No guideline names keystroke monitoring or Accessibility. Related: 2.5.14 requires "explicit user consent and ... a clear visual and/or audible indication when recording, logging, or otherwise making a record of user activity ... or other user inputs"; 5.1.1(ii)/(iii) require consent and data minimisation.
- **Fact (documented rejection).** A sandboxed clipboard manager that only uses `CGEvent.post` (PostEvent, no AX APIs) was rejected twice under 2.4.5, the reviewer stating "Accessibility features should not be used for non-accessibility purposes" (Mar 2026). DTS confirmed the technical side is sandbox-compatible but cannot speak for App Review and told the developer to raise it with App Review. Another developer reported the same rejection in Sep 2026; no resolution is recorded ([thread 820594](https://developer.apple.com/forums/thread/820594)).
- **Fact (precedent).** TypeIt4Me 7 is a new Mac App Store app (first released 2025-04-18, seller Riccardo Ettore, macOS 12.4+) whose listing says abbreviations "typed almost anywhere on your Mac ... will instantly expand" ([App Store](https://apps.apple.com/us/app/typeit4me-7/id6474688391?mt=12); release date from the iTunes lookup API). Its developer says it was "rebuilt ... from scratch in Swift, fully sandboxed", "still needs to be granted Accessibility Access in order to expand typed abbreviations", and that App Review is inconsistent: some reviewers "have initially rejected them point blank on seeing the access request" ([developer comment on mjtsai.com](https://mjtsai.com/blog/2025/04/24/typeit4me-7/); [Ettore announcement](https://ettoresoftware.store/2025/04/18/typeit4me-7-out-now-special-launch-price-9-99/)). This is the closest precedent to Pāli Key: system-wide capture plus erase-and-retype.
- **Fact (precedent, mechanism unverified).** Rocket Typist, a text expander first released on the store 2023-10-12 and still updated in Nov 2026 ([App Store](https://apps.apple.com/us/app/rocket-typist/id6463636684)). Its listing mentions expanding abbreviations; how it inserts text on Mac was not verified.
- **Fact (no IME route).** An InputMethodKit input method, the "native" macOS way to build Pāli Key, cannot be distributed on the Mac App Store: "your only option is to distribute outside of the Mac App Store" (DTS, 2020, reaffirmed Apr 2026, [thread 134115](https://developer.apple.com/forums/thread/134115)).

### Why Magnet and BetterSnapTool are not counterexamples

- **Fact.** Magnet was first released on the store 2011-06-10, BetterSnapTool 2011-02-25 ([Magnet](https://apps.apple.com/us/app/magnet/id441258766?mt=12), [BetterSnapTool](https://apps.apple.com/us/app/bettersnaptool/id417375580?mt=12), dates from the iTunes lookup API). Sandboxing became mandatory for new Mac App Store submissions on 2012-06-01 ([MacRumors, 2012](https://www.macrumors.com/2012/02/21/apple-extends-deadline-for-sandboxing-of-mac-app-store-apps-to-june-1)).
- **Fact.** Quinn: "Not all Mac App Store apps are sandboxed. Some apps shipped on the store before sandboxing was required", check with `codesign -d --entitlements -` ([thread 707680](https://developer.apple.com/forums/thread/707680), Sep 2025). For a new window manager in Oct 2025 he wrote: "It's not possible to use the Accessibility APIs from a sandboxed app ... your only path forward here is to directly distribute your app using Developer ID signing" ([thread 805556](https://developer.apple.com/forums/thread/805556); also [thread 836644](https://developer.apple.com/forums/thread/836644), Jul 2026).
- **Inference.** Magnet and BetterSnapTool predate the deadline and are most likely grandfathered unsandboxed apps (not checked with `codesign` here). Their usage is materially different too: window managers need the full `Accessibility` privilege (AXUIElement write APIs), which the sandbox blocks, whereas Pāli Key needs only `ListenEvent` and `PostEvent`. So the earlier claim "sandboxed apps cannot get Accessibility" is right for the AX APIs and wrong for event posting, which shares the same System Settings pane.

## 3. Entitlements and temporary exceptions

- **Fact.** No special entitlement is needed for event taps or posting: the only one involved is `com.apple.security.app-sandbox`; access is granted by the user through TCC ([thread 789896](https://developer.apple.com/forums/thread/789896)).
- **Fact.** `com.apple.security.accessibility` "isn't a thing" (Quinn, [thread 805556](https://developer.apple.com/forums/thread/805556)).
- **Fact.** Full Accessibility in a sandboxed app is not possible "without employing temporary exception entitlements" ([thread 780626](https://developer.apple.com/forums/thread/780626)). Pāli Key should not need any temporary exception, and should not request one.

## 4. Secure Event Input and recognising our own events

- **Fact.** "When secure event input is enabled, keyboard input will only go to the application with keyboard focus, and will not be echoed to other applications that might be using the event monitor target to watch keyboard input." Password controls enable it automatically. `IsSecureEventInputEnabled()` reports whether any process has it on (`HIToolbox/CarbonEventsCore.h`, macOS 27.2 SDK).
- **Inference.** In password fields (and while any app holds secure input) the tap sees no keystrokes, so no Replacement happens there. That matches the Windows behaviour users would expect. The Status Indicator could show when secure input is blocking Pāli Mode; a known side effect is that an app that forgets to disable secure input silently stops Pāli Key everywhere.
- **Fact.** Events carry `kCGEventSourceUserData` ("event source user-supplied data, up to 64 bits") and `kCGEventSourceUnixProcessID` (`CoreGraphics/CGEventTypes.h`; [Apple docs](https://developer.apple.com/documentation/coregraphics/cgeventfield/eventsourceuserdata)).
- **Inference.** Post Replacement events from a dedicated `CGEventSource` with a fixed user-data marker (`CGEventSourceSetUserData`) and have the tap ignore events carrying that marker (or whose source pid is our own). This is the macOS equivalent of the Windows `LLKHF_INJECTED` / `dwExtraInfo` check.
- **Fact.** Taps can be disabled by the system and are told so via `kCGEventTapDisabledByTimeout` / `kCGEventTapDisabledByUserInput` (`CGEventTypes.h`); the callback must re-enable the tap and stay fast.

## Caveats and recommended next steps

1. **App Review risk is real and not controllable.** Expect a possible 2.4.5 rejection because the PostEvent prompt is labelled "Accessibility". Prepare App Review notes that explain: only `ListenEvent` and `PostEvent` are used, no AX APIs, no keystrokes are stored or transmitted, Pāli Mode is user-toggled with a visible Status Indicator (2.5.14), plus a short demo video. Be ready to appeal, citing DTS in [thread 820594](https://developer.apple.com/forums/thread/820594).
2. **Prototype first, sandboxed, on a clean macOS 13 VM:** listen-only tap + posted Backspace/Unicode events, own-event tagging, secure-input behaviour, and which TCC prompts appear. Check whether an active tap prompts for something the sandbox blocks.
3. **Keep a fallback:** Developer ID (notarized) distribution outside the store is always possible if App Review refuses.
4. Optional: run `codesign -d --entitlements -` on Magnet, BetterSnapTool and TypeIt4Me 7 to confirm their sandbox status (not done here).
